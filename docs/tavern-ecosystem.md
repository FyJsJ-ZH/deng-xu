# 酒馆生态整合评估

> 七件东西：酒馆助手、提示词模板、柏宝书、故事神谕、cocktail、cocktail-plus、柏宝箱。
> 外加三张顶级卡组的发布页截图（《大凉龙虎传》125 可攻略角色、《命定之诗与黄昏之歌》
> 西幻 RPG、《苍玄界》240 角色 + CG 收集 + 悬浮球状态栏）。
>
> 对着 `pale-notes-web` 现在的代码逐项过一遍，判断哪些能内化、哪些该换形态、哪些根本不该碰。

---

## 零、结论先放在这里

| 东西 | 它在生态里的位置 | 对 pale-notes 的判断 |
|---|---|---|
| **酒馆助手**（JS-Slash-Runner） | 运行时引擎 | **不需要** —— 我们自己就是宿主 |
| **提示词模板**（ST-Prompt-Template） | 模板层 | **换形态做** —— 要「动态世界书」，不要「提示词里跑 JS」 |
| **柏宝书**（ST-BaiBai-Book） | 记忆层 | **值得做，而且已经有一半** |
| **故事神谕**（story-oracle） | 旁路 AI | **值得做，我们完全没有** |
| **cocktail** | 宿主性能 | 不碰 |
| **cocktail-plus** | 宿主性能 | 不碰，而且是反面教材 |
| **柏宝箱**（ST-BaiBai-Tools） | 宿主性能（+ 三条可抄） | 抄三条，其余不碰 |

一句话概括：**这七件里，五件是在给一个十年前的前端应用打补丁**。
SillyTavern 是一个巨大的 jQuery 单体，所以它需要 Service Worker 拦截 `/version`、
需要在 `script.js` 之前 patch `window.fetch`、需要用 `content-visibility` 修剪长聊天 DOM。
pale-notes 是 React 18 + Vite + zustand，没有那些历史包袱，**照抄这些等于给自己找病**。

剩下两件（柏宝书、故事神谕）是**能力层**的东西，那才是真差距。

---

## 一、把七件摆到同一张图上

SillyTavern 本身**没有插件系统**。它只有「角色卡 + 世界书 + 预设 + 正则」四样静态数据。
所以整个社区生态是在**外面套了一层运行时**，一层一层加上去的：

```
L6 性能层     cocktail / cocktail-plus / 柏宝箱          给宿主本身的迟滞打补丁
L5 旁路 AI    story-oracle                              第二个模型，独立窗口，不碰主聊天
L4 记忆层     柏宝书                                    摘要 / 台账 / 向量召回
L3 模板层     ST-Prompt-Template                        提示词里跑 EJS，世界书条目能条件渲染
L2 运行时     酒馆助手（JS-Slash-Runner）+ MVU 变量框架   变量状态机 / 前端脚本 / 状态栏
L1 数据       角色卡 · 世界书 · 预设 · 正则              静态文本
L0 宿主       SillyTavern                               一个大型 jQuery 前端 + Node 后端
```

**看懂这张图，后面的判断就都顺了。**

三层以下的每一层，都在补同一个洞：**L1 是死的**。
世界书条目是纯文本，没法「到了第三年才生效」，没法「好感度过 50 才解锁这段」，
没法「这个角色只知道你告诉过他的事」。L2 和 L3 就是来把死文本变活的。

而 pale-notes 从一开始就把 L2 做在了自己身体里（zustand store + 数据 AI 的 JSON 结算协议），
所以 L2 那层整件不需要。

## 二、逐件拆解

### 2.1 酒馆助手（JS-Slash-Runner）

**它是干什么的**：在 iframe 里执行第三方 JavaScript，绕过 SillyTavern「不支持跑脚本」的限制。

**它在生态里的真实地位，比它的名字大得多。** 从故事神谕的更新日志能看出来 ——
里面反复出现「酒馆助手 → MVU 变量框架面板」「酒馆助手的变量更新引擎」这类说法。
也就是说，**整个社区的状态机（`stat_data`、变量更新块、状态栏）是跑在酒馆助手上的**。

它提供了：
- 变量读写（`getvar` / `setvar` 那套的前身）
- 变量更新块的解析与写入（MVU）
- 状态栏渲染（把 HTML 塞进消息里）
- 前端 UI 注入点

**对 pale-notes**：不需要。我们已经有：
- 变量 → `src/stores/gameStore.ts`（zustand）
- 结算 → `buildDataSystemPrompt` 的 JSON 协议 + `useGameEngine.ts`
- 状态栏 → 原生 React 组件

**但要记一笔**：社区之所以堆这么多层，是因为**宿主给不了**。
这反过来说明 pale-notes 一开始把机制做进内核是对的 —— 这条路走对了。

### 2.2 提示词模板（ST-Prompt-Template）

**它是干什么的**：在任何送给模型的文本里跑 EJS（`<% %>`）。世界书条目、角色卡、预设都能用。

核心能力：
- `<%- getvar('affinity') %>` 把变量插进提示词
- `<% if (...) { %> ... <% } %>` 条件分支
- **响应后处理**：模型输出里的 `<% setvar(...) %>` 会被执行，于是 AI 的正文能改状态
- `[GENERATE:BEFORE]`：世界书条目可以指定插在提示词的哪个位置
- `@INJECT`：按正则/相对位置插入整条 message

**它解决了什么**：世界书条目从「静态段落」变成「渲染出来的段落」。
一条写着「如果好感度 > 50 就说这句」的条目，只在满足条件时才出现。
**这就是酒馆卡能做出 RPG 系统的技术底座。**

**对 pale-notes**：**这个概念必须吸收，这个实现不该照抄。**

在提示词里执行任意 JS 有四个后果，一个比一个糟：
1. 世界书变成**可执行代码**。玩家导入一份别人的世界书 = 跑一段陌生人的脚本。
2. 「为什么这一轮没注入那段设定」变成一个查不动的问题 —— 得读 JS 才知道。
3. 模板出错没有好报错，只有模型吐出一堆 `<% %>` 原文。
4. 同一份世界书无法被静态检查（我们现在有 `check-worlds.mjs`、`check-encoding.mjs` 这类守卫，全都会失效）。

**该做的形态**：声明式条件块。给世界卡加一个受限的语法，比如：

```yaml
- when: { resource: 好感, op: '>=', value: 50 }
  text: 她终于肯叫你名字了。
- when: { chapter: '>=', value: 3 }
  text: 城门口的告示换了新的。
```

条件只有「资源比较 / 属性比较 / 章节 / 有无某标签 / 有无某物品」这几种，
**可枚举、可静态校验、可写进类型**。这能覆盖酒馆卡 95% 的实际用法，
却仍然是数据而不是代码。

成本：中等（类型 + 渲染函数 + 编辑器 UI + 校验脚本）。收益：世界书从静态变半动态。

### 2.3 柏宝书（ST-BaiBai-Book）

**它是干什么的**：长期记忆引擎。这个是他列的东西里**信息密度最高**的一件。

它维护的台账有八本：

| 台账 | 记什么 |
|---|---|
| 剧情摘要 | 每楼自动摘要 → 多层总结 → 概览（三层压缩） |
| 故事内时间 | 每个摘要带时间锚点，防「昨天的事被当成三年前」 |
| 物品 | 谁获得/消耗了什么、东西放在哪儿、随身还是寄存，带变动日志 |
| 角色 | 登场人物身份/外貌/穿着/状态，自动分级（主演/路人） |
| 生活小档案 | 主角与主要角色的偏好习惯，标明所属人物，不跨人物合并 |
| **好感双轨** | 内在倾向 + 外在态度各五档，另有「未知」 |
| **角色对你的了解** | 每个角色一份「他知道你的什么」，没记过的私事默认不知道 |
| 场景 | 去过的地点按大小做成一棵地图树 |
| 计划与悬念 | 约定、伏笔、未解谜题单独记，了结就核销 |

还有：向量记忆（按需召回，多角度检索 + 精排打分）、副 API（摘要用便宜模型）、
内容清洗（剔思维链和状态栏）、换对话带数据。

**对 pale-notes**：**这是唯一一件我认为必须补的**，而且我们已经有了一半。

`src/utils/memory.ts` 现在的三层：

| 我们的层 | 语义 | 柏宝书对应 |
|---|---|---|
| `bonds` | 关系现状（谁欠谁） | 关系台账（部分） |
| `threads` | 悬而未决（承诺/债务/威胁） | 计划与悬念簿 |
| `timeline` | 按轮次的事实 | 剧情摘要 |
| `summary` | 连贯叙述 | 多层总结 |

**缺的四样，按价值排序**：

1. **角色对你的了解** —— 这条最值钱，因为它防的是「NPC 全知」。
   现在 `formatCharacter()` 把 `description` / `personality` / `scenario` 整段给模型，
   于是任何一个 NPC 都天然知道你的一切。这个 bug 和之前踩过的「替玩家认亲」
   是同一类：**模型把设定当成了角色的认知**。
2. **场景地图树** —— 现在只有 `location` 一个字符串字段，换三个地方就记不住谁在哪。
3. **物品台账** —— `items` 是「世界的预置物品」，不是「谁手里有什么、放在哪」。
4. **好感双轨** —— 「心里喜欢你但嘴上不承认」这件事，单轨表达不了，而它恰恰是最好写的戏。

向量召回先不做。理由见第五节。

### 2.4 故事神谕（story-oracle）

**它是干什么的**：一个独立窗口，接你自己的 API，**在播放过程中问剧情**。

六种模式：普通聊天 / 诊断（修变量）/ 世界书（直接改世界书）/ 剧情参谋（悄悄引导主聊天）/
校正（去 AI 味）/ 角色工坊（聊出一个 NPC 写进世界书）。

**它最值钱的一条设计，不是功能，是「不碰主聊天」。**

理由很实在：你在玩的时候，想问「她为什么这么做」。
如果直接问主模型，那条提问会进 history，成为后续叙事的上下文 —— 剧情被污染了。
所以它开一个**独立窗口、独立历史**，读主聊天但**只读**。

第二条值钱的是**「校正」的工序**。它的做法细到：
- 划选一段、只改这一段，按字符偏移精确回插，没划到的字**压根不进模型**
- 改完先给 diff 看，确认才应用，原文留在 swipe 里
- 专门的「去 AI 味」五个目标：AI 八股 / 对话机械 / 过度精确 / 魔法被写成理科 / 描写拖沓
- 自动模式带**禁词预筛 + 字数下限**，本来干净就不发起调用

**对 pale-notes**：完全没有，而且**正好对上你的偏好**。

你现在关心的是「文字要有味、不要套路」。现在唯一的控制手段是 `customStyle`
（一段写在世界卡里的文风要求）。而神谕的做法是：**写完再修一遍，且只改该改的地方**。

落地形态建议（不要照抄六种模式，只做三种）：
1. **旁路问答**：问剧情、问设定，只读 history，不进主对话
2. **去 AI 味**：对最新一条回复做一次校正，生成新 swipe，原文保留
3. **查设定**：拿关键词去 worldLore 里翻，回答「这城里有没有当铺」

第 4 种「剧情参谋（悄悄引导主聊天）」**先不做** —— 它和「沙盒优先」的设定直接冲突，
我们的提示词里明令「不要催、不要替玩家推进剧情」，再插一个暗中引导的机制是自相矛盾。

### 2.5 cocktail

三个前端优化合并：启动加载、聊天渲染、正则刷新。

**对 pale-notes**：无意义。这三样对应的问题我们都不存在
（Vite 冷启动几百毫秒、消息列表是虚拟滚动之外的普通列表、正则我们只有很轻的一套）。

### 2.6 cocktail-plus

Service Worker 拦截 `/version` 与 `/api/characters/all`、后端插件做磁盘缓存、
在 `script.js` 之前 patch `window.fetch`、Early Bridge 往 `index.html` 里插脚本。

它解决的是：SillyTavern 的 `/version` 会跑六条 git 命令，启动就卡几百毫秒；
角色多的时候 `/api/characters/all` 要几秒。

**对 pale-notes**：不碰，而且**这是反面教材**。

它为了省几百毫秒，往宿主的 `index.html` 里注入脚本、patch 全局 `fetch`、
用 Service Worker 改道请求。这类改动的代价是**整个应用的请求路径变成不可推理的** ——
以后再出「为什么这个请求没发出去」的问题，你得先想起还有个 SW 在中间。

我们已经踩过类似的坑（§4.6d 的构建版本探测、§4.6j 的内容指纹），
但那些都在**我们自己的代码里**，看得见、测得着。cocktail-plus 这种不属于此列。

### 2.7 柏宝箱（ST-BaiBai-Tools）

一长串 UI 层补丁：长聊天 `content-visibility`、头像懒加载、正则 Vue 分组管理器、
CodeMirror 编辑器、Token 计数批量化、聊天保存 Gzip、生成失败重试、黑名单重试、
完成提示音、后台生成（save-generate）。

**对 pale-notes**：绝大多数无意义。但有**三条值得抄**：

1. **黑名单命中自动重试**。我们已有 `llmRetry.test.ts`（429 / 500 那套重试），
   但那是**请求层面**的重试。柏宝箱这条是**内容层面**的：回复正文命中黑名单
   （比如返回了 `HTTP 503` 或一段道歉模板）就重新生成。
   我们的场景里对应的是「模型返回了一段拒绝话术」或「返回了空正文」。
2. **移动端静音保活**。生成期间循环播一段内联静音音频，降低手机切后台被冻结、
   导致回复丢失的概率。我们是纯前端 + IndexedDB，切后台丢回复是真会发生的。
3. **生成后置保存（save-generate）**。它把生成完成后的写入放在后端，
   防「前端拿到回复但没来得及存」。我们没有后端，做不了；
   但可以在 `useGameEngine` 里**生成完成立刻落盘、不等下一轮**。
   需要确认现在是不是这个顺序。

## 三、三张卡组截图说明的事

三张图是酒馆生态的天花板：《大凉龙虎传》（125 个可攻略角色）、《命定之诗与黄昏之歌》
（西幻 RPG）、《苍玄界》（240 角色、20 主 NPC、108 个开场、100+ CG、悬浮球状态栏、
地图、拍卖行、功法收集、创意工坊）。

三张卡都写着同一句：「**请务必安装酒馆助手（更新到最新版）和提示词模板**」。

这句话本身就是结论：**这生态的能力上限，不在世界书写得多好，在你装了几个插件。**

### 3.1 世界书的两种组织方式

对照着看，这才是这一节的重点：

| | 酒馆卡的世界书 | pale-notes 的 worldLore |
|---|---|---|
| 组织单位 | **条目**，几百条，每条 200–800 字 | **散文**，26–36 章，每章 1000–1500 字 |
| 触发 | 关键词命中才注入（绿灯），或常驻（蓝灯） | 按情境摘录，**命中的整章**注入 |
| 规模 | 一本卡几百条 | 一部世界 3–8 万字 |
| 优势 | 精准、省 token、可以一个人物一条 | 连贯、有整体感、能看到「这个世界怎么运转」 |
| 劣势 | 条目之间容易打架，缺整体感 | **检索粒度粗** |

我们之前定的「志书」路线（`世界书制作要求.md`）是对的 —— 酒馆卡那套条目化世界书，
写不出「这个城怎么运转」。但**我们的检索粒度确实粗**。

### 3.2 真差距不是角色数量

240 角色 vs 我们的 15 角色，这个数字差距不用追 —— 酒馆卡的 240 个角色，
大部分是「一个人物一条」。我们一部世界 15 个 `CharacterCard`，
但每个都有 120–260 字的外貌 + 100–200 字的性情 + 客观立场。
**信息量不比它少，只是组织方式不同。**

真正的差距在这一句：**用户想要一个新角色时，能不能自己加。**

《苍玄界》写的是「只要拥有图床链接和人设想法，想要的角色就会被写入世界书，成为苍玄界的一员」。
这就是它的创意工坊。而我们有完整的卡片编辑器（`CardEditor` + `lookSpec` + 250 个 LPC 部件），
**这一块我们比它强**，因为立绘是我们自己渲染的，不依赖图床。

| 能力 | pale-notes 现在有什么 | 缺口 | 建议 |
|---|---|---|---|
| 变量状态机 | `gameStore` + 数据 AI JSON 协议 | — | **已达标** |
| 状态栏 | 原生 React 组件 | — | **已达标** |
| 世界书条件渲染 | 无（`rules` 是纯文本） | 大 | 做声明式条件块（2.2） |
| 世界书检索 | `loreDigest.ts`，**按章**切分，关键词打分 | **粒度粗** | **降到段级**（5.1） |
| 剧情摘要 | `summary` + 三层记忆 | — | 已达标 |
| 关系台账 | `bonds` | — | 已达标 |
| 悬念台账 | `threads` | — | 已达标 |

| 场景地图树 | 只有 `location` 字符串 | 大 | 加地点层级 |
| 物品台账 | `items` 是预置物品 | 中 | 加持有/位置 |
| **角色对你的了解** | 无 | **大** | **优先做**（5.3） |
| 好感双轨 | 单轨（`bonds.state` 是字符串） | 中 | 拆内外两档 |
| 向量召回 | 无（**有意不做**） | — | **先不做**（5.4） |
| 旁路 AI | 无 | 大 | 做三种模式（5.2） |
| 回复校正 | 无 | 大 | 同上，并入旁路 |
| 请求重试 | `llmRetry.ts`（429/500） | 内容层重试 | 抄柏宝箱的黑名单重试 |
| 手机端保活 | 无 | 小 | 抄静音保活 |
| 提示词执行 JS | 无 | — | **不做** |

## 五、值得做的三件，按投入产出排序

### 5.1 世界书检索：把粒度从「章」降到「段」

**成本最低，收益最大，先做这个。**

现在 `splitLore()` 按行首独占一行的 `**标题**` 切章。一章 1200 字。
只要这一章命中一个专名（比如提到「汴梁」），**整章 1200 字全进提示词**。

问题不是贵，是**稀释**：一段讲漕运的、一段讲物价的、一段讲讼案的，
只有一段对眼前这轮有用，另外 800 字在无关地占用注意力。

**改法**：

1. `splitLore()` 先切章，再在章内按**空行**切成段（现在每章本来就分了 3–8 段）。
2. 打分单位从「章」变成「段」，仍用现有的专名命中法。
3. 命中的段，**连带前后各一段**一起注入（滑窗，防止把上下文切掉）。
4. 落选段落进索引时，仍然只给「章标题 + 首段首句」—— 不然索引本身会膨胀。

`loreDigest.test.ts` 现在 16 条，改成段级之后需要补：
- 段级打分是否正确
- 滑窗（前后邻段）是否带上
- 索引字数是否没有膨胀
- 章节内首段是否仍然「无条件保留」

**为什么这个比向量检索更值得先做**：它不改变可解释性。
出问题时你仍然能说「因为这一段里出现了『汴梁』和『漕渠』」。

### 5.2 旁路 AI（只做三种模式）

**这是我们现在完全没有、而且最能提体验的一件事。**

形态：一个侧边抽屉，独立 API 调用（可以用更便宜的分析模型），
**读 `useGameEngine` 的 history，但绝不写入**。

三种模式：

| 模式 | 做什么 | 为什么值 |
|---|---|---|
| **问剧情** | 「她为什么这么做」「我们之前答应过什么」 | 玩家在玩的时候有疑问，直接问主模型会污染上下文 |
| **去 AI 味** | 对最新一条回复重写一遍，生成新 swipe | 直接对上「文字要有味」这个长期诉求 |
| **查设定** | 拿关键词翻 worldLore，回答「这城有没有当铺」 | 比让玩家去翻世界书友好一百倍 |

**关键实现约束**（从神谕那边抄经验）：
- 独立 history，不写进主对话（一次都不许）
- 校正类操作**只生成新 swipe，不动原文**（原文永远能划回去）
- 校正前先跑**禁词预筛 + 字数下限**：本来干净的回复不发起调用，省钱
- 划选校正要按**字符偏移精确回插**，没选中的字不进模型（这是它最硬的一条）

不做的模式：**剧情参谋（暗中引导主聊天）**。理由前面说过 ——
和我们的「沙盒优先 / 不要催」直接冲突。

### 5.3 角色对你的了解（防全知）

这条单独拿出来说，因为它是**一个 bug 的正式修法**。

现在所有 NPC 都知道你的一切，因为 `formatCharacter()` 把整张卡塞给模型。
你觉得某个 NPC 对玩家底细门儿清 —— 那不是模型聪明，是它读了世界书。

**改法**：

1. `StoryMemory` 加一层：

```ts
/** 每个角色对玩家的认知：角色 id → 他已知的事实条目 */
knownBy: Record<string, string[]>
```

2. 数据 AI 的 JSON 协议加一个动作：`LEARN_FACT { who, fact }`，只在剧情里明确发生
   「你告诉了他」「他查到了」「他亲眼看见了」时才记。
3. 注入时（`memoryInjection`）按**当前在场角色**过滤，只把该角色名下的条目给他的档案块。
4. 每个角色档案块末尾加一句：
   「**以上是他知道的事。此外他一无所知** —— 他不知道玩家的身世、来历、秘密、
   没当面说过的事。若剧情需要他提到这些，必须有来源（有人告诉他、他查过、他亲眼见过）。」

这条和之前那版「不要替玩家认亲」是同一个方向：**把模型的默认全知按住**。

成本：中等偏小。`memory.ts` 加一层 + 数据 AI 加一个动作 + `formatCharacter` 改签收 + 一批测试。

### 5.4 向量召回：先不做

`loreDigest.ts` 里已经写明了为什么不做，那段理由**仍然成立**：

> 这是关键词命中，不是语义检索 —— 它挑不出「讲的是同一件事但用词不同」的章节。
> 之所以仍然这么做：判据完全可解释，出问题时能一眼看出是专名清单缺了词、
> 还是某一节写得太泛。换成向量检索会让「为什么这轮没注入物价那一节」变成一件查不动的事。

柏宝书的向量记忆做得很细（多角度检索 + 精排打分 + 只在需要时召回），
但它运行在一个**你没法调试的黑盒**里 —— 它的用户是真的不知道「为什么这段想起来了」。

我们先做 5.1（段级检索）。如果段级做完还是不够准，再考虑向量 ——
那时候的依据会具体得多：我们会知道是「专名清单不够全」还是「真的需要语义」。

## 六、明确不做的四件

| 不做 | 理由 |
|---|---|
| 酒馆助手式的脚本运行时 | 我们不是插件宿主，我们是应用。变量就是 store |
| 提示词里执行任意 JS | 世界书会变成可执行代码，全部静态守卫失效 |
| cocktail / cocktail-plus | 它们修的是 SillyTavern 的历史包袱，我们没有那些包袱 |
| 剧情参谋（暗中引导） | 与「沙盒优先 / 不要催」直接冲突 |

**特别说第三条**：不要因为「人家做了所以我们也该有」就去抄性能补丁。
判断标准很简单 —— **问一句「我们有没有那个问题」**。
`content-visibility` 修剪长聊天 DOM？我们的消息列表一屏几十条，不用。
Service Worker 拦 `/version`？我们的构建版本探测（§4.6d）已经解决了。

## 七、三条可以立刻抄走的小东西

### 7.1 内容层重试（黑名单）

柏宝箱的做法：读完本轮回复正文，命中黑名单就重新生成，**不增加候选**、不重复发用户消息。

黑名单支持两种写法：
- 普通行：正文包含该文本即命中（忽略英文大小写）
- `/正则/标志` 行：按正则匹配

我们可以用的默认黑名单（按我们的实际情况）：
- `/^\s*$/`（空回复）
- `作为(一个)?(AI|人工智能)`（拒答话术）
- `/^\s*(很抱歉|抱歉)[，,]/`（道歉开场）
- `HTTP\s*(4\d\d|5\d\d)`

和现有 `llmRetry.ts` 的分工：那个管**请求失败**，这个管**请求成功但内容是垃圾**。
两者共用「本轮最多重试 N 次」的计数，不各算各的。

### 7.2 手机端静音保活

生成期间循环播放一段内联静音音频（base64 wav，几百字节），
降低浏览器切后台后冻结页面、导致回复写不回来。

只在「移动端 + 生成中」启动，生成结束就停。成本几乎为零。

### 7.3 生成完成立刻落盘

确认 `useGameEngine` 里的顺序：**回复写进 store 之后，是不是立刻 `queuePersist()`**。
如果是等下一轮才存，那么这次生成一断网就没了。
柏宝箱专门做了后端 save-generate 来防这件事，我们没后端，但可以做到「拿到就存」。

## 八、如果只做一件事

**做 5.1（世界书段级检索）。**

理由：
- 它是现有九部世界书**立刻就能受益**的改动，不用等新世界
- 成本最低（改一个函数 + 补测试）
- 它修的是一个我们**已经知道存在**的问题：一轮只用到一段，却注入了整章
- 它不需要新 UI、不需要新 API、不影响任何其它模块

第二件做 5.3（角色对你的了解），因为它修的是一个**行为 bug**，不是缺功能。

第三件做 5.2（旁路 AI），因为它最大、也最能提体验，但要有前两件垫底。
